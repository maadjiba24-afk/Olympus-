## Domain thesis

Colibri's deepest asset is not a kernel — it is an **engineering system in which every claim is
load-bearing**: comments cite the measurement and the issue that justified them, dead ideas are
buried with written eulogies instead of deleted, docs are generated from the only place truth lives
(`getenv()` sites), CI's cheapest job is the one that proves correctness, and even the marketing
site's demo is a paced replay of a real measured run. Olympus independently evolved the same
culture — drift-gated capability counts (`capabilities.py`), `DEFERRED.md`'s "deferral is allowed;
silent deferral is not", the re-executable decision log, `gate_prompt` auto-rollback — but its
versions are narrower than Colibri's in exactly the places a small team bleeds: the drift gate
covers four counts but not ~200 env vars; negative results live in prose, not in a machine-checked
registry; releases are signed but never behaviorally exercised post-build; and demos/product
surfaces have no formal honesty rule at all, despite Olympus owning the one substrate (signed,
replayable runs) that could make demo honesty *verifiable* rather than merely asserted. This
absorption formalizes the culture into gates, because in the `MOAT_ANALYSIS.md` frame the culture
IS the asset-quality guarantee: the Calibration Record is only worth its multi-year integral if
every entry's provenance discipline holds, and provenance discipline is exactly what this domain
mechanizes.

## 1. Measurement-justified code comments with issue provenance

**1. What Colibri does.** Nearly every optimization in `colibri.c` carries its justification inline:
the measured number ("matmul 66.9→20.9 s", "26→63 GB/s, 2.4×"), the GitHub issue (`#471`, `#413`),
and often the failure story ("an inherited one-core mask jailed the whole team"). Frozen constants
are declared spec ("the constants are the spec", pinned by tests). See analysis §3.1, §5, §26.1.

**2. Why it exists.** A single maintainer + drive-by contributors: the comment is the only durable
transfer medium for *why*, and a number is the only argument that survives a rewrite proposal.

**3. How it works internally.** Pure convention, socially enforced in review; issues `#NNN` act as
the provenance ledger; some claims are additionally frozen as regression tests (§23: "int3 must
beat int4 on outlier-seeded rows").

**4. Strengths.** Reverse-engineering the repo *is possible from comments alone* (the deep-analysis
doc proves it). Deleting a guarded line requires refuting a measurement, not an opinion. Claims that
matter get promoted from comment → test, the strongest form.

**5. Weaknesses & trade-offs.** Unenforced: nothing detects a stale number after hardware or code
changes; provenance points at a mutable external system (GitHub issues can be edited/deleted);
the convention is invisible to tooling — no way to query "all claims justified by #442".

**6. Security implications.** Mild positive: security boundaries annotated with the attack they
block (`#413` byte-count-exact format resolution) resist "simplification" refactors that reopen holes.

**7–8. Scalability & performance implications.** None at runtime; scales poorly socially — beyond
a few maintainers the convention needs a linter or it decays.

**9. Maintainability implications.** The core value: the codebase is self-arguing. But comment-borne
measurements rot silently — Colibri has no staleness signal.

**10. How Olympus redesigns it.** Adopt the convention; fix the rot problem by anchoring provenance
in things Olympus already version-controls and gates: a claim in a comment must cite either (a) a
`docs/adr/NNNN-*.md`, (b) a `DEFERRED.md` row, (c) a `CHANGELOG.md` entry, or (d) a committed
measurement artifact (`quality_baseline.json` `_provenance`, a `docs/CALIBRATION_*` report, a
replay-gate run) — all in-repo, diffable, and staleness-visible. Where the claim is load-bearing,
promote it to a test (the Colibri idiom Olympus already uses: `test_deps_claim` enforces the
three-dependency README claim).

**11. Final Olympus architecture.** No new module. (a) A "measurement-provenance" section in
`CONTRIBUTING.md`: *any comment asserting a measured or empirical fact names its in-repo source;
numbers with no source are opinions and may be deleted.* (b) The review checklist (and the
auto-upgrade workflow's PR template) gains the line "empirical claims cite ADR/DEFERRED/CHANGELOG/
baseline." (c) `docs/DECISION_LOG.md` stays the runtime-provenance twin: code decides, trace records.
The existing house style already does this well (DEFERRED #19's baseline-refresh note is exactly a
Colibri-grade eulogy); this codifies it so it survives contributor turnover.

**12. Why superior.** Colibri's provenance lives half outside the repo (issues); Olympus's lives
entirely in version control, is covered by the drift-gate culture, and its strongest claims are
executable (tests, replay gates, committed baselines) rather than prose.

## 2. Negative results preserved as opt-ins + the EXPERT_BUDGET quarantine (grouped)

*Grouped honestly: these are one pattern at two intensities — "measured worse, kept behind a flag
with a written eulogy" (n-gram drafting, PREFETCH, XEXP-on-small-boxes, the 6×5090 rejected-with-data
list, §10.4) and "measured catastrophic, kept behind a double opt-in with the eulogy printed in
`main()`" (`EXPERT_BUDGET`, §6.3/§26.4: hellaswag 30% vs 90%, MTP acceptance 0%, *and slower* —
"empty operating window", gated on `EXPERT_BUDGET_EXPERIMENTAL=1`).*

**1–3. What/why/how.** Complete features that lost their benchmarks are never deleted: they ship
default-off with the measured verdict written where the flag is read, so the next person with the
same idea finds the corpse and the coroner's report before re-implementing it. Mechanism: env-gated
code paths + comments + (for the worst) a startup banner and a second confirmation variable.

**4. Strengths.** Institutional memory that compounds — precisely the "accumulated asset" shape
MOAT_ANALYSIS values. Kills idea-recycling cost, the dominant waste in small teams. The code stays
testable (the quarantined path still compiles and runs under its flag).

**5. Weaknesses & trade-offs.** Dead-flag inventory grows unboundedly; nothing verifies eulogies
against the current code (the operating window may reopen after an unrelated change — Colibri
explicitly flags one such inversion, §10.4's "MTP inverts if TC grouped GEMM lands" — but nothing
*re-tests* it); the registry is grep-shaped, not machine-readable; quarantined code silently rots
if no test exercises the flagged path.

**6. Security implications.** Dormant code paths are attack surface. Colibri accepts this; Olympus
must not — a quarantined *tool or action* would still need `cmdguard`/approval-spine coverage, so
the registry must be visible to the threat-model gate (`scripts/check_threat_model.py`).

**7–9. Scalability/performance/maintainability.** No runtime cost when off (env check). The
maintainability risk is the inverse of the benefit: an unindexed graveyard becomes noise. Colibri's
own §27 shows the failure mode — quarantines documented in four different places (comments,
CHANGELOG, ENVIRONMENT.md, main()) with no single source.

**10. How Olympus redesigns it.** Olympus already has the prose half: `DEFERRED.md` ("deferral is
allowed; silent deferral is not", stable row IDs, empirical closure notes) and `evolve.py`'s bounded
self-tuning. What's missing is the *mechanized* half: a single machine-readable registry binding
every experimental flag to its eulogy and its re-test condition, drift-gated like capability counts.
Every Colibri weakness becomes a gate: unregistered flags fail CI (no unindexed graveyard); each
entry carries a `revisit_when` condition (the reopening problem becomes a documented trigger);
each entry names the benchmark that condemned it (the eulogy is re-runnable, not prose).

**11. Final Olympus architecture.**
- **New module `olympus/experiments.py`** — a small registry, `capabilities.py`-style:
  `EXPERIMENTS: dict[str, Experiment]` where `Experiment = {flag, status: "experimental" |
  "quarantined", eulogy, evidence (ADR/DEFERRED row/eval run ref), revisit_when, owner_date}`.
  `experiments.check()` scans `olympus/*.py` for `OLYMPUS_EXPERIMENTAL_*` reads and fails on any
  flag absent from the registry (the same scan machinery as the env-docs gate in §3 below).
- **Naming convention:** quarantined features read `OLYMPUS_EXPERIMENTAL_<NAME>=1`; the *worst*
  class additionally requires `OLYMPUS_I_READ_THE_EULOGY=1` — Olympus's double opt-in, and the
  activation prints the eulogy (Colibri's `main()` banner, translated).
- **Manifest integration:** `capabilities.py:manifest()` gains an `"experiments"` section
  (count + names + status), so `capabilities.json` and the CI gate cover it with zero new workflow.
- **`DEFERRED.md` evolves, not replaced:** rows stay the human ledger; a row that gates code now
  names its registry key, and `experiments.check()` verifies the cross-reference.
- **Re-test hook:** `evolve.py`/heartbeat may, on an operator-set cadence, re-run a quarantined
  entry's condemning benchmark when its `revisit_when` names a changed precondition (e.g. "primary
  model family changed" — checkable against `config.default_model()`); results append to the entry.
  This is bounded and opt-in — no autonomous un-quarantining; promotion is a human PR.
- **Threat-model coupling:** `check_threat_model.py` treats quarantined tools/actions as live
  surface (they are).

**12. Why superior.** Colibri's graveyard is greppable; Olympus's is *queryable, drift-gated, and
re-runnable*. And because Olympus's "features" are prompts/skills/routing policies as often as code,
the same registry gives the self-improvement loop (Prometheus/`gate_prompt`) a place to bury its
own rejected rewrites with their before/after scores — negative results from the *autonomous* loop
accumulate in the same asset, which Colibri (no self-modification) never needed but Olympus does.
Beyond Colibri: the eulogy is a signed measurement reference, not a comment.

## 3. Generated docs from getenv sites + the MAINTAINING-DOCS procedure

**1. What Colibri does.** `docs/ENVIRONMENT.md` (~130 env vars, defaults, rationale) and
`SETTINGS.md` are *generated by scanning every `getenv()` call site*; `MAINTAINING-DOCS.md`
documents an AI-assistant-oriented regeneration procedure — "truth lives only at `getenv()` sites…
If a knob isn't at one of those call sites, it isn't real" — with a proposed-but-unimplemented CI
drift check (§24, §25).

**2. Why it exists.** ~130 knobs, one maintainer: hand-maintained reference docs are guaranteed
lies within a month. Generation from code makes the doc a projection of truth.

**3. How it works internally.** Scanner over source for `getenv` sites; the procedure doc tells a
future maintainer (explicitly including an AI assistant) how to regenerate and what invariants to
keep. The drift check is acknowledged as missing — docs can still go stale between regenerations.

**4. Strengths.** The doc cannot describe knobs that don't exist; the "AI-assistant procedure"
insight is ahead of its time — docs written to be *maintained by agents* need explicit invariants,
not tribal knowledge.

**5. Weaknesses & trade-offs.** The one weakness is fatal and admitted: **generation without a
gate**. Colibri built exactly the trap Olympus's `capabilities.py` docstring warns about (Ruflo:
"generating baselines is not enough; the prose must be bound"). Also: rationale text isn't at the
getenv site, so the scanner produces the skeleton and a human backfills prose that can rot; and
`SETTINGS.md`'s CLI surface is a second, separately-drifting projection.

**6. Security implications.** Real: an undocumented env knob is an unaudited control channel
(Colibri's own `TEMP`-vs-`$TEMP` incident, §26.3, is what happens when the env surface isn't fully
inventoried). A generated, gated inventory is the precondition for the threat model to claim
coverage of the configuration surface.

**7–9. Scalability/performance/maintainability.** Zero runtime cost. The maintainability win is
the whole point; the scanner itself is trivial for a convention-disciplined codebase (Olympus is:
`grep OLYMPUS_` is nearly the whole inventory already; `config.py` alone has 72 environ reads).

**10. How Olympus redesigns it.** Extend the *existing, already-gated* capability manifest rather
than building Colibri's ungated generator: `capabilities.py` learns to scan `olympus/*.py` for
`OLYMPUS_*` environ reads (AST walk over `os.environ.get/[]`, `os.getenv`, `secretref.getenv`),
producing an `"env"` manifest section and a generated `docs/ENVIRONMENT.md`. The gate Colibri
proposed and never built is the gate Olympus already runs on every push (`olympus capabilities
--check` in ci.yml and the RELEASING checklist) — this absorption is literally "finish Colibri's
TODO using Olympus's existing mechanism."

**11. Final Olympus architecture.**
- `olympus/capabilities.py`: new `_env_vars()` collector → `{"env": {"count": N, "names": [...],
  "sites": {var: [module, ...]}}}` in `manifest()`; the committed `capabilities.json` and the
  existing `check()` staleness rule extend automatically (schema_version bump to 2).
- Rationale lives *at the site* Colibri-style: a same-line or preceding `#: doc:` comment is
  harvested as the description; vars lacking one are listed under "undocumented" and a CI budget
  (`--max-undocumented`, ratcheting down) prevents regression without demanding a big-bang backfill.
- Generated `docs/ENVIRONMENT.md` with a "GENERATED — edit the code, not this file" header;
  `docs/MAINTAINING-DOCS.md` adopted nearly verbatim as the agent-facing procedure (Olympus is
  *maintained by* coding agents via auto-upgrade.yml — Colibri's AI-assistant framing is native here).
- CLI settings reference: `command_names()` already exists; a `--help`-dump projection into
  `docs/CAPABILITIES.md` reuses the same gate. One truth pipeline, three projections (README counts,
  env reference, CLI reference).
- The scanner is shared with `experiments.check()` (§2) — one AST pass, two gates.

**12. Why superior.** Colibri generated but never gated; Olympus gates by reflex. And because
`check_threat_model.py` and the security gate consume the same manifest, the env inventory upgrades
from documentation to *audited attack-surface census* — a claim Colibri's ENVIRONMENT.md cannot make.

## 4. Oracle-first CI split (check / ci / release)

**1–3. What/why/how.** Colibri's CI (§22) is layered by what each layer can honestly prove:
`check.yml` runs the full token-exact oracle suite (`make check`) on the three OSes it can truly
execute; `ci.yml` adds *syntax-only* GPU compiles, loudly labeled as such, with the memorial
comment about the `| head -40` that once masked every error — "a check that cannot fail is worse
than no check"; `release.yml` verifies the shipped artifact behaviorally. What CI cannot execute
(GPU kernels) is explicitly delegated to maintainer/community hardware, acknowledged in §22.

**4. Strengths.** Honesty about coverage: every job's name tells you what its green means. The
cheap deterministic oracle (32/32 teacher-forcing on the tiny fixture) gates everything; expensive
or unexecutable checks are additive, never load-bearing lies.

**5. Weaknesses & trade-offs.** No sanitizers/fuzz/coverage jobs (admitted); syntax-only GPU legs
can pass while kernels are broken (mitigated only socially); the split lives in workflow files, not
a documented contract, so a contributor can't tell which failures are gating.

**6–9. Security/scalability/performance/maintainability.** The upload-the-Windows-artifact-per-PR
countermeasure (#527/#532 antivirus saga) shows the split doubling as a *community-verification*
channel. Maintainability: three small honest workflows beat one omnibus; the risk is drift between
what docs claim CI does and what it does.

**10. How Olympus redesigns it.** Olympus already has the superior decomposition — and should now
*document it as a contract*: `ci.yml` (deterministic architecture/gates/security tests — the
oracle layer; matrix + browser/docker legs that self-skip locally per `docs/TESTING.md`),
`replay-gate.yml` (the decision-path oracle: re-execute recorded runs, byte-identical decisions —
Olympus's exact analog of teacher-forcing 32/32), `quality-gate.yml` (LLM-scored, noise-bounded via
`evals.confirm_regressions` — the layer Colibri *couldn't* have, since its quality oracle is exact),
`publish.yml` (release). The absorption items: (a) the "a check that cannot fail is worse than no
check" audit — grep the workflows for any step whose failure is swallowed (`|| true`, missing
`needs`, advisory-only jobs not labeled advisory) and label or fix each; (b) the honesty rule that
what CI cannot execute is *named* (Olympus's version of "no hosted GPUs": no live-provider quality
runs on PRs — quality is gated on `main`/schedule with real keys, and TESTING.md says so, which it
already largely does).

**11. Final Olympus architecture.** No new modules. A short "CI contract" section in
`docs/TESTING.md`: for each workflow, *what a green run proves and what it cannot prove* —
mirroring Colibri §22's table. One concrete gate addition: `pytest -q` job asserts the skip count
against a committed ceiling (TESTING.md admits a fresh checkout can "silently skip a few hundred
tests" — that is a check that cannot fail; bind it: `--max-skips` budget per CI leg, ratcheted).

**12. Why superior.** Colibri's oracle is token-identity on a fixture; Olympus's replay gate is
decision-path identity on *real recorded runs* — the same determinism doctrine applied to a
stochastic substrate, which is strictly harder and already built. Absorbing the split costs a
documentation section and one skip-budget assertion, not new infrastructure.

## 5. Release behavioral verification + staleness stamps (grouped)

*Grouped honestly: `release.yml`'s unpack-and-run step and the `.build-config` relink stamp are the
same invariant at two build stages — "the artifact you ship is the artifact you think you built"
(§21: the stamp exists because a stale CPU-only binary once shipped silently, #306/#478; the
behavioral step exists because v1.1.0's banner crash shipped past unit tests).*

**1–3. What/why/how.** `release.yml` builds the three-platform archive, then **unpacks it in a
clean directory and runs `coli info`** — a smoke execution of the *shipped* artifact, not the
build tree — plus `SHA256SUMS.txt` and CHANGELOG-extracted notes. `.build-config` is a Make stamp
file recording the flag set; any change forces relink, so a binary can never silently carry stale
build flags.

**4. Strengths.** Caught a real shipped-broken release (the banner failure). The stamp closes the
classic incremental-build lie. Both are cheap (seconds) relative to the failure they prevent
(a broken release under users' `curl | sh`).

**5. Weaknesses & trade-offs.** `coli info` is a shallow probe — it proves the binary starts, not
that serving works; the stamp guards *build* staleness but nothing guards *runtime* staleness
(a user's old binary against new docs). Verification runs in the same CI environment that built
the artifact — no cross-environment install proof.

**6. Security implications.** SHA256SUMS + per-PR artifact upload turned an antivirus false-positive
crisis into a verifiable-by-anyone process (§26.1). Olympus is already ahead here (Ed25519-signed
`verification.json`, pinned pubkey, `olympus verify`) — the absorption is behavioral, not
cryptographic.

**7–9. Scalability/performance/maintainability.** Trivial cost. Maintainability win: the release
checklist stops depending on maintainer memory for "did anyone actually run the wheel?"

**10. How Olympus redesigns it.** Olympus signs releases (`publish.yml` → `olympus sign`) and has
an operator-run reliability gate (`scripts/reliability_gate.py`), but **nothing between "wheel
built" and "wheel on PyPI" ever executes the wheel** — exactly Colibri's pre-fix gap, and worse:
Olympus's wheel carries a signed manifest whose integrity `olympus verify` checks, so a packaging
error (missing data file, broken entry point, manifest/file drift) is both more likely to be caught
*and* currently unchecked. Close it with a clean-venv behavioral job. Translate the staleness stamp
to Olympus's actual staleness risks: (a) an editable-install dev tree whose installed metadata
version ≠ `pyproject.toml` (the Python analog of a stale relink); (b) committed measurement
artifacts aging past their honesty window (`quality_baseline.json` `_provenance.date` — DEFERRED
#19 is precisely a staleness-stamp incident, resolved manually; give it a warning light).

**11. Final Olympus architecture.**
- `publish.yml` gains a `verify-artifact` job between build and upload: fresh venv →
  `pip install dist/*.whl` → run, offline and keyless, `olympus version`, `olympus capabilities
  --check`, `olympus verify` (against the wheel's own signed manifest), and `olympus doctor --json`
  asserting only offline checks pass — a superset of `coli info`'s probe. Failure blocks upload.
  `RELEASING.md` step 5.5 documents it.
- `olympus/doctor.py` gains two staleness checks (warn, not fail): **install-staleness** (installed
  distribution version vs source `pyproject.toml` when running from a checkout) and
  **baseline-staleness** (`quality_baseline.json` `_provenance.date` older than
  `OLYMPUS_BASELINE_MAX_AGE_DAYS`, default 90 — the DEFERRED #19 refresh procedure becomes a
  doctor-surfaced routine instead of a discovered drift).
- `selfupdate.py` (`olympus upgrade`) already handles user-side freshness; doctor cross-references
  it when a newer release exists.

**12. Why superior.** Colibri proves the artifact *starts*; Olympus proves the artifact starts,
self-verifies its signed integrity, and carries non-drifted capability claims — behavioral,
cryptographic, and provenance checks in one pre-upload gate. The staleness principle generalizes
from build flags to measurement provenance, which is the staleness that actually bites an
API-client system (baselines rot; binaries don't).

## 6. Community-datapoint governance & the performance-report template

**1–3. What/why/how.** Colibri's headline numbers are *community-sourced, each linked to a GitHub
issue* (§1, §20): a dedicated performance-report issue template demands commit, hardware/storage,
env, commands, warm-up policy, run count, medians, and profile timings; `docs/benchmarks.md` opens
"everything on this page is a measurement, not a promise" and every row cites its issue. Governance:
single maintainer, PRs to `dev`, community datapoints as the evidence base (§1).

**4. Strengths.** Converts users into a distributed measurement lab with provenance discipline;
the template *is* the methodology (medians, warm-up policy) so datapoints are comparable; claims
degrade gracefully — a doubted number has a named source to re-run.

**5. Weaknesses & trade-offs.** No verification of submitted numbers (trust-based); hardware
diversity confounds comparison; the corpus lives in issues — queryable by humans, not machines;
selection bias (people report successes and outrages, not the middle).

**6. Security implications.** Low for Colibri. For Olympus, community *quality* datapoints can
embed prompts/outputs — the template must mandate the contribution-anonymization discipline that
`contrib.py` already implements for the cross-model pool (strip PII/keys at write time).

**7–9. Scalability/performance/maintainability.** Scales exactly as far as maintainer triage;
the template keeps triage O(read), which is the point.

**10. How Olympus redesigns it.** Olympus's scarce measured resource is not tok/s but **council
quality per dollar across providers** — and its moat thesis (Asset 2) says the accumulating blind
record of "which model serves this workload" is the defensible output. So the community datapoint
Olympus wants is a *quality/cost report*: version, provider+model (from `_provenance`-style
metadata), `olympus scores`/`olympus eval` output, spend (`usage.py`), and — the Beyond-Colibri
part — an optional **replay bundle reference**, because a recorded run can be re-executed
(`olympus verify --log <run_id>`), making a community datapoint *checkable*, which Colibri's never
were. Coordinate, don't duplicate: absorption 09 already claims the perf-report intake
(`support.py`, `.github/ISSUE_TEMPLATE/perf-report.yml`); this rubric adds the quality-report twin
and the shared governance rule.

**11. Final Olympus architecture.**
- `.github/ISSUE_TEMPLATE/quality-report.yml`: required fields — `olympus version`, provider/model,
  `olympus scores` paste, eval item set (built-in vs custom), run count + medians, spend, opt-in
  anonymization confirmation; optional signed-run reference.
- `olympus/support.py`: `olympus report --quality` pre-fills the template from local state
  (version, model, latest scores, spend) exactly as `olympus report --perf` does in absorption 09 —
  one command, both templates, shared plumbing.
- Governance rule in `CONTRIBUTING.md`: **no number enters README/docs prose without either a
  `cap:` binding, a `_provenance` block, or a linked report issue** — the Colibri benchmarks.md
  doctrine, stated once, gated where bindable.
- Accepted datapoints append to `docs/CALIBRATION_RECORD.md`'s evidence lists, feeding Asset 1.

**12. Why superior.** Colibri's datapoints are honest but unverifiable; Olympus's carry optional
cryptographic replay-ability and feed a governed, anonymized pipeline that already exists
(`contrib.py`, `quality_baseline.json` provenance). The community lab reports on the dimension the
moat analysis says compounds: cross-provider quality on real workloads.

## 7. The honest replay demo & product-surface honesty rules

**1. What Colibri does.** The site's "watch it think" demo (§16) is an **honest replay**: a fixed
real transcript paced at *measured* community decode rates, synchronizing a fake terminal, a heat
canvas, and the expert galaxy — with an on-page disclaimer and issue links: "nothing here is
invented."

**2. Why it exists.** A 0.05–2 tok/s engine cannot demo live on a web page; the alternative
(a sped-up fake) would poison the project's entire measurement-first credibility. The demo is
marketing built to the same fidelity doctrine as the engine.

**3. How it works internally.** Self-contained static HTML; the transcript, pacing rates, and
atlas data are embedded real measurements; the disclaimer names sources.

**4. Strengths.** The only demo in the category that can survive an adversarial reader. Cultural
coherence: a user who later runs the engine gets *exactly* what the demo showed, at their
hardware's rate.

**5. Weaknesses & trade-offs.** Honesty is *asserted*, not verifiable — a reader must trust the
disclaimer; the replay is hand-assembled (regeneration is manual labor, so it will age); one
transcript = one cherry-pickable sample, and nothing states the selection policy.

**6. Security implications.** Minor; a demo pipeline that replays real transcripts must scrub
credentials/PII from them — for Olympus this is mandatory, since real runs contain user data.

**7–9. Scalability/performance/maintainability.** Static and free to serve; rots as the product
evolves unless regeneration is scripted.

**10. How Olympus redesigns it.** Olympus holds the card Colibri lacks: **every run is already a
signed, content-addressed, re-executable record** (`replaystore.py`, `trace.py`, the decision log).
So the honesty rule can be *mechanical*: a demo is not "a transcript we promise is real" but a
replay of run `<id>` whose decision path anyone can re-verify (`olympus verify --log <run_id>`).
Each Colibri weakness inverts: assertion → cryptographic verifiability; hand-assembly → generated
from the store; cherry-picking → the demo metadata states the selection policy and N. This respects
ROADMAP §0's replay boundary (F9): demos are *audit replay* — re-rendering a recorded run — never
counterfactual re-execution, and are labeled as recordings.

**11. Final Olympus architecture.**
- **New module `olympus/demo.py`** (small): `record(run_id) -> demo bundle` — extracts the
  transcript + per-stage timings + spend from `trace.py` records, scrubs via the same redaction
  path `contrib.py`/`httpcapture` use, and emits a self-contained bundle (JSON + optional static
  HTML player reusing `transcript.py`/`web.py` rendering); `play(bundle)` paces output at the
  *recorded* timings in the TUI.
- CLI: `olympus demo record [run_id]`, `olympus demo play [bundle]`. `--label` is not optional:
  every rendered frame carries "RECORDED RUN <short-id> · <date> · model <m>" — the disclaimer is
  emitted by the renderer, not left to the page author.
- **Product-surface honesty rules** (one short section in `docs/VISION.md`, binding on README,
  web.py/pwa.py, and any future site): (1) demos are labeled replays of real runs; (2) timings
  shown are measured, never dramatized; (3) any quality number on a surface traces to a `cap:`
  binding, `_provenance`, or a report issue (§6's rule); (4) demo bundles state selection policy.
- Env: `OLYMPUS_DEMO_DIR` (bundle store, default under the memory dir).

**12. Why superior.** Colibri's demo is honest; Olympus's is *provably* honest — the disclaimer
upgrades from prose to a verifiable reference, which is exactly the Asset-1 discipline (signed,
causally-anchored evidence) applied to marketing. Beyond Colibri: demos double as onboarding
fixtures (`play` needs no API key), giving keyless first-run users a real-behavior tour for free.

## 8. CLI ergonomics: banner, attach mode, two-stage Ctrl-C, markdown stream renderer

**1–3. What/why/how.** `coli chat` (§13, §26.12): ANSI pixel-art banner; **attach mode** — a
millisecond `/health` probe decides between attaching to an already-running warm server (measured
4%→55% cache hit, ~10×) and spawning a private engine; **two-stage Ctrl-C** (first interrupts the
current generation, second exits); a **streaming-markdown renderer with split-marker hold-back**
(markers arriving across chunk boundaries are held until disambiguated); OOM-kill forensics in
`engine_diag()`; `coli web` polls `/health` up to 20 min because "the 744B engine takes minutes to
load."

**4. Strengths.** Attach mode converts an architectural fact (warm state is precious) into a
zero-config UX win. Two-stage Ctrl-C matches user intent (stop *this*, not the session). Hold-back
rendering solves the real streaming-markdown bug everyone else ships. Diagnostics assume failure
will happen and pre-collect the forensics.

**5. Weaknesses & trade-offs.** Attach is heuristic (port probe) — a wrong process on the port
confuses it; single-tier fallback only; the renderer is hand-rolled and grows edge cases; the
20-minute poll papers over absent progress reporting.

**6. Security implications.** Attaching to a socket means trusting what answers it; Olympus must
authenticate the attach (the web/gateway surfaces already carry tokens) and never send a vaulted
key to an unverified local server.

**7–9. Scalability/performance/maintainability.** Attach mode is *the* performance feature —
Olympus's analog is real: a running heartbeat/web process holds warm memory caches, embedding
indexes (`annindex`), session state, and a primed store, while a cold CLI invocation re-reads all
of it; multi-process store contention is exactly the `proclock` problem ADR 0005 documents.

**10. How Olympus redesigns it.** `tui.py` already has multiline input, autocomplete, and
streaming; `cli.py` has 16 bare `except KeyboardInterrupt` sites and no staged-interrupt policy.
Absorb: (a) **attach mode** — `olympus` probes `health.py`'s endpoint on the configured web/gateway
port (authenticated); if a live Olympus answers, the REPL becomes a client of the warm process
(reusing the existing web chat API) instead of constructing a cold council; `--no-attach` opts out;
this also *reduces* the Windows multi-process store problem (DEFERRED #10) by making one process
the writer. (b) **Two-stage Ctrl-C** — first ^C cancels the in-flight council run *gracefully*:
the orchestrator's cancellation must still write the partial trace/ledger records (an aborted run
is evidence, not garbage — Asset 1 discipline) and print "interrupted — ^C again to exit"; second
^C within the window exits. (c) **Hold-back streaming renderer** — `tui.py` gains a pure,
unit-testable `MarkdownStream` that withholds ambiguous trailing marker fragments (``` ` ``,
`**`, fence openers) until the next chunk resolves them — pure function, tested like `read_block`.
(d) Banner: keep Olympus's existing minimal identity; a banner is culture, not architecture —
adopt only a one-line status footer (model · provider · session · attach state), which is the
informative part of Colibri's banner.

**11. Final Olympus architecture.** `olympus/tui.py`: `MarkdownStream` renderer + staged-interrupt
helper (pure, injectable clock); `olympus/cli.py`: attach probe at REPL start (env
`OLYMPUS_ATTACH=auto|off|<url>`, default auto), wiring ^C stages through the orchestrator's
existing cancellation path; `olympus/health.py`: the probe endpoint already exists — add an
identity field so the client verifies it attached to *Olympus* (instance id from `identity.py`)
before sending anything. No new modules.

**12. Why superior.** Colibri's warm state is a cache; Olympus's warm state is *memory, indexes,
and session context*, so attach mode pays in quality and latency at once — and by funneling
interactive traffic through the already-governed web pipeline, attach mode strengthens (not
bypasses) the approval spine and single-writer store discipline. Interrupts that persist partial
traces turn user impatience into calibration evidence.

## 9. Desktop-shell minimalism

**1–3. What/why/how.** Colibri's desktop app (§15) is a 12-line Tauri shell around the web build:
no commands, no plugins, no sidecars, no model downloads — rationale stated in the README: "the
model is hundreds of gigabytes and must remain an external, user-selected resource rather than an
opaque application sidecar." The shell's one functional delta is a *tighter* CSP (connect-src
localhost only).

**4. Strengths.** Near-zero maintenance surface; the heavy resource stays user-owned and
inspectable; the shell adds security rather than capability.

**5. Weaknesses & trade-offs.** Defers real desktop value (engine lifecycle, tray, notifications)
— admitted; a shell that thin must justify existing at all.

**6–9. Security/scalability/performance/maintainability implications.** The doctrine *is* the
security posture: every capability the shell doesn't have is an attack class it doesn't carry.
Maintenance cost ≈ 0, which for a small team is the difference between having a desktop story and
abandoning one.

**10–11. How Olympus absorbs it.** Olympus already made this exact choice: `pwa.py` is the
installable shell over `web.py`, with no separate desktop codebase — and the Colibri translation of
"the model stays external" is "**the API key and the memory store stay external, user-selected
resources**": no Olympus surface bundles credentials or wraps the store in an opaque app container.
Action: state the doctrine in one paragraph (docs/VISION.md "product surfaces" section, alongside
§7's honesty rules) so future "ship an Electron app" proposals argue against a written decision;
if a native shell is ever added, it follows Colibri's contract — shell adds *constraints* (CSP,
loopback-only), never capabilities. Verdict: **absorb-principle**; no code.

**12. Why superior.** Same doctrine, stronger justification: Olympus's heavy resource is the user's
*data and credentials*, where opacity is a governance violation, not just an inconvenience.

## 10. i18n

**1–3. What/why/how.** Colibri (§14.4, §24, §11.3): a hand-rolled 4-locale provider in the web UI
(en, zh-CN, zh-TW, it); READMEs translated into four languages; and the deepest item —
`getenv_utf8` reading the Windows *wide* environment because the ANSI codepage corrupted
Cyrillic/CJK prompts *before the byte-level tokenizer ever saw them*: i18n as data integrity, not
translation.

**4. Strengths.** The `getenv_utf8` class of fix is the right priority: correctness of non-ASCII
*data paths* before UI translation. Static translations are cheap goodwill for a hobbyist audience.

**5. Weaknesses & trade-offs.** Four hand-maintained READMEs are four drift liabilities in a
project whose core doctrine is generated-docs-or-it-rots — Colibri's own §27 lists doc drift among
its limitations; hand-rolled string tables scale badly past a few locales; UI chrome is dark-only,
en-default.

**6–9.** No security impact; maintainability is the whole trade — every translated static artifact
is a fork of the truth.

**10–11. How Olympus absorbs it.** Olympus's `i18n.py` is architecturally ahead: coordination runs
in English (cheaper, schema-reliable), while **every user-visible word is generated natively in
the user's language** — translation-by-generation needs no string tables and covers all languages
the model speaks, across CLI/web/Telegram alike. Absorb two things: (a) the **data-integrity
lesson** — audit the non-ASCII path end-to-end (Windows console encoding in `cli.py`/`tui.py`
(`PYTHONIOENCODING`/UTF-8 mode), gateway byte handling, store round-trips); add a non-ASCII
round-trip test through the transcript/store path — Olympus's `getenv_utf8` equivalent; (b) *UI
chrome* (the fixed labels of `web.py`/`pwa.py`) may adopt a minimal locale map keyed off the
`prefs` language, since generated text already follows the user. **Consciously skip** translated
READMEs/docs: hand-maintained translations violate the drift-gate culture (rule of this domain:
no ungated projection of truth), and Olympus's actual product surface is already per-user
multilingual where it counts. Verdict: **absorb-principle**, translated static docs **skip** with
reason.

**12. Why superior.** Colibri translates artifacts; Olympus generates natively per user — no
tables, no drift, every language. The one thing Colibri did that Olympus must copy is treating
encoding as integrity, and that is a test, not a subsystem.
