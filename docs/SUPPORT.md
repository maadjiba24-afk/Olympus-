# Support, versioning & release integrity

Olympus commits to a predictable release cadence and a verifiable supply of
artifacts — the stability Ruflo's 1,500-plus-release churn lacks. This document
is that promise.

## Versioning (SemVer)

Olympus follows [Semantic Versioning](https://semver.org/) — `MAJOR.MINOR.PATCH`:

- **MAJOR** — incompatible changes to the CLI surface, the public Python API
  (`olympus.orchestrator`, `olympus.actions`, …), or the on-disk memory format
  (`schema_version`). Always called out in the changelog with a migration note.
- **MINOR** — new, backward-compatible capabilities (a new specialist, tool, or
  command). The capability manifest (`olympus capabilities`) and the README
  numbers move together, enforced by CI.
- **PATCH** — backward-compatible bug fixes and security patches only.

The single source of truth for the current version is `pyproject.toml`.

## LTS window & patch policy

| Line | Status | What it receives |
| --- | --- | --- |
| Current MINOR | Active | Features, fixes, and security patches. |
| Previous MINOR | Maintained (LTS window) | Security and critical-correctness fixes for **6 months** after the next MINOR ships. |
| Older | End-of-life | No updates — upgrade to a maintained line. |

Security fixes are released as a PATCH on every maintained line. The on-disk
memory format is migrated forward, never silently broken (`olympus memory
migrate`; see `docs/MEMORY_FORMAT.md`).

## Release integrity — signed releases & `olympus verify`

Every published release ships a **signed witness manifest** (`verification.json`,
generated by the publish workflow and included in the wheel). It lists every
tracked package file with its SHA-256, plus the git commit, and is signed with
an Ed25519 key (using the `cryptography` dependency Olympus already ships — no
new dependency). See `olympus/witness.py`.

```bash
olympus sign               # generate verification.json over the package
olympus verify             # recompute every hash, check the signature
olympus verify --manifest <path>
```

`olympus verify`:

1. recomputes each tracked file's SHA-256 and **fails, naming any drifted or
   missing file**;
2. checks the manifest's Ed25519 signature, so altering the file list or hashes
   is caught;
3. re-derives the public key from the signing seed and rejects a manifest
   **re-signed with a foreign key** — so an attacker can't tamper-and-resign.

The root of trust is an Ed25519 key derived from `OLYMPUS_SIGNING_SEED`
(`ed25519(sha256(seed))`). Set it as a secret in the publish workflow for an
authentic key; the built-in default seed is public, so manifests signed under it
are marked `dev` and rejected for release unless `--allow-dev` is passed. Pin the
production public key (`OLYMPUS_PINNED_PUBKEY` or `witness_pubkey.txt`) so a
manifest re-signed with any other key fails verification. **Full key-custody
procedure: see [docs/SIGNING.md](SIGNING.md).**

## Signed decision log (one root of trust)

The **same** key signs the Task-1 decision log. Every run's decision path is
signed at flush time (`trace.flush` → `witness.sign_log`), so the audit trail is
tamper-evident:

```bash
olympus verify --log <run_id>   # check a recorded run's decision-log signature
```

If any recorded decision is altered after the fact, the signature check fails.
This is what Ruflo signs for trajectories — Olympus signs the **whole** decision
log, the thing you replay (`olympus replay`) and now also prove untampered.

## Release-readiness reliability check (operator-run)

CI proves *recorded* runs replay; before a release, prove the harness works
**unattended end-to-end on a real key** with the reliability gate:

```bash
python scripts/reliability_gate.py
# or with your own cap / prompts:
OLYMPUS_DAILY_BUDGET=10 python scripts/reliability_gate.py "p1" "p2" "p3"
```

It runs three distinct prompts through the full pipeline, and for each confirms
a decision log was produced and that the run replays **zero new API calls and
byte-identically** (`orchestrator.replay_run` → empty diff). It enforces a spend
cap (`OLYMPUS_DAILY_BUDGET`, default $5) and prints each `run_id`, a per-run
PASS, and the total spend. Exit 0 = all three replayed reproducibly under the
cap; a provider/credit problem reports INCONCLUSIVE (not a failure). Needs
`ANTHROPIC_API_KEY`, so it's run by the operator, not in offline CI.

## Reporting issues & vulnerabilities

File issues at the repository tracker. For suspected security issues, prefer a
private report (see `SECURITY.md`) over a public issue so a fix can ship first.
